# Service Catalog Feature — API Reference

> Source: `src/features/service-catalog/**`. Generated by reading every file in the module
> (models, controllers, services, routes, validators, constants) plus the mounting chain
> (`src/app.js` → `src/routes/v1/index.js` → `src/features/service-catalog/index.js` →
> `src/features/service-catalog/routes/index.js`) and the shared `auth` middlewares
> (`authenticate.js`, `checkPermission.js`) and response utilities (`ApiResponse`, `ApiError`,
> `globalErrorHandler`). This document is meant to be self-contained — a frontend/integration
> developer should not need to open the backend source.

---

## 1. Overview

The service-catalog module implements a four-level admin-managed catalog hierarchy:

```
Category  →  Subcategory  →  ServiceGroup  →  Service
```

Every level except `Service` (which is a leaf) can have children at the next level, and every
level below `Category` denormalizes its ancestor IDs (e.g. `Service` stores `serviceGroup`,
`subcategory`, AND `category`) so list/filter queries don't need to populate the whole chain.
Denormalized ancestor fields are **derived automatically** in Mongoose `pre('save')` hooks from
the immediate parent — they are not accepted as client input for that purpose (see per-model
notes below).

Two additional entities hang off this hierarchy:

- **AddOn** — an optional extra a customer can attach to a booking, linked to *exactly one* of a
  `Service` or a `ServiceGroup` (never both, never neither). Add-ons have no vendor
  request/approval flow of their own; they simply "inherit" availability from whatever vendor is
  approved to offer the linked `Service`.
- **VendorService** — the join/request entity that lets a `Vendor` ask to offer a catalog
  `Service`. A vendor can only browse the catalog and *request* to offer a `Service`; they never
  set price and never go live until an `Admin` approves the request. This is a
  pending → approved / rejected state machine (see section 4).

**Authoring model:** All catalog structure (`Category`, `Subcategory`, `ServiceGroup`, `Service`,
`AddOn`) is created/edited/deleted exclusively by **Admins**. Vendors and end users only have
read (`GET`) access to these, plus the vendor-only request flow on `VendorService`. There is a
separate `media` sub-route (admin-only) that generates presigned upload URLs for direct
browser-to-object-storage image uploads used by the catalog entities' `image`/`images` fields.

**Ambiguous / notable:** No route in this module uses `checkPermission(resource, action)`
(the sub-role permission gate). Every admin-gated route uses only
`requireIdentity(IDENTITIES.ADMIN)`, meaning **any** authenticated actor whose top-level identity
is `admin` — regardless of `subRole`/granular permissions — can perform every admin action in this
module (create/update/delete on all catalog levels, add-ons, presigned media URLs, and
approve/reject vendor requests).

## 2. Data models

All models live under `src/features/service-catalog/models/`. Mongoose is registered under
custom names (see `constants/modelNames.constants.js`) to avoid `OverwriteModelError` collisions
with same-named legacy models already registered elsewhere in the codebase (`src/models/`):

| Exported JS name | Registered Mongoose model name | Why |
|---|---|---|
| `Category` | `CatalogCategory` | legacy `Category` model already exists elsewhere |
| `Subcategory` | `Subcategory` | no legacy equivalent — kept plain |
| `ServiceGroup` | `ServiceGroup` | no legacy equivalent — kept plain |
| `Service` | `CatalogService` | legacy `Service` model already exists elsewhere |
| `VendorService` | `CatalogVendorService` | legacy `VendorService` model already exists elsewhere |
| `AddOn` | `CatalogAddOn` | legacy `AddOn` model already exists elsewhere |

This matters only for anyone writing raw Mongoose `populate()`/`ref` code against these
collections outside the feature — from the HTTP API's perspective it's invisible.

All models use `{ timestamps: true }` (`createdAt`, `updatedAt` on every document).

### AddOn (`CatalogAddOn`)

An extra item a customer can attach to a booking, linked to exactly one of `Service` or
`ServiceGroup` so add-ons stay contextually relevant (e.g. AC add-ons don't show under a salon
service). No vendor request/approval — add-ons inherit availability from the vendor's approved
`VendorService` for the linked `Service`.

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `name` | String | yes | — | trim, maxlength 100 |
| `description` | String | no | — | maxlength 500 |
| `price` | Number | yes | — | min 0 |
| `image` | embedded `image` schema or `null` | no | `null` | |
| `service` | ObjectId, ref `CatalogService` | no* | `null` | *exactly one of `service`/`serviceGroup` must be set — enforced (see below) |
| `serviceGroup` | ObjectId, ref `ServiceGroup` | no* | `null` | |
| `isActive` | Boolean | no | `true` | |
| `createdBy` / `updatedBy` | ObjectId, ref `Admin` | yes / no | — | |

A `pre('validate')` hook enforces **exactly one** of `service`/`serviceGroup` is set — XOR, not
both, not neither — throwing `ApiError(400, 'Add-on must be linked to exactly one of service or serviceGroup')`
if violated. (The Zod validators also enforce this at the HTTP boundary before it ever reaches the
model — see endpoint docs — so this model-level check is mainly a defensive backstop.)

Indexes: `{ service: 1, isActive: 1 }`; `{ serviceGroup: 1, isActive: 1 }`.

## 3. Endpoints

**Mounted base path for every endpoint in this module:** `/api/v1/service-catalog`

Mount chain confirmed by reading:
- `src/app.js`: `app.use('/api', router)` where `router` is `src/routes/v1/index.js`.
- `src/routes/v1/index.js`: `router.use('/v1/service-catalog', serviceCatalogFeatureRoutes)` where
  `serviceCatalogFeatureRoutes` is `src/features/service-catalog/index.js` → re-exports
  `src/features/service-catalog/routes/index.js`.
- `src/features/service-catalog/routes/index.js` mounts each sub-router at:
  `/categories`, `/subcategories`, `/service-groups`, `/services`, `/add-ons`, `/vendor-services`, `/media`.

So e.g. the categories list route is `GET /api/v1/service-catalog/categories`.

**Auth envelope reminder** (from `src/features/auth/middlewares/authenticate.js` and
`checkPermission.js`):
- `authenticate` reads the access token from the `accessToken` cookie or an `Authorization: Bearer <token>`
  header, verifies it, rejects blacklisted/revoked tokens, loads the actor onto `req.user`, and
  sets `req.identity` (one of `user` / `vendor` / `admin` — `IDENTITIES` constant) and
  `req.tokenJti`/`req.tokenExp`. Throws `401 Access token missing`, `401 Access token has been revoked`,
  `401 Invalid access token`, or `403 Account is blocked`.
- `requireIdentity(...identities)` (used throughout this module) gates on `req.identity` matching
  one of the given identities, else `403 Requires identity: <identities>`.
- `checkPermission(resource, action)` (defined in auth, **not used anywhere in service-catalog**)
  would additionally gate on an admin's `subRole` permission — not applicable here, see the
  Overview ambiguity note.

**Response envelope reminder:**
- Success: `ApiResponse` → `{ statusCode, data, message, success: true }` (all examples below show
  the full wrapped body).
- Error (from `globalErrorHandler`): `{ success: false, status: <code>, message, errors?: [...] }`
  — note the key is **`status`**, not `statusCode`, and there is **no `data` key** on error
  responses. In `development` NODE_ENV a `details: { stack, errorType }` key is also added. Zod
  validation failures (`validate` middleware) produce `errors: [{ field: 'body.name', message }, ...]`.
  Mongoose `CastError` → 400 "Invalid ID format...", duplicate key (`code 11000`) → **400** "Duplicate
  value for field '<field>'..." (not 409 — only service-layer business-rule conflicts described below
  use 409), `ValidationError` → 400 with per-field messages.

### 3.1 Categories — `/api/v1/service-catalog/categories`

#### `GET /api/v1/service-catalog/categories`
- **Access:** public (no `authenticate`).
- **Query (`listCategoriesSchema`):**
  | Field | Type | Required | Default | Constraints |
  |---|---|---|---|---|
  | `page` | number (coerced) | no | `1` | int, positive |
  | `limit` | number (coerced) | no | `20` | int, positive, max 100 |
  | `isActive` | string | no | — | enum `'true' \| 'false'` |
- **Success 200:**
  ```json
  {
    "statusCode": 200,
    "data": {
      "items": [
        {
          "_id": "665f1c2e8b1e4a2a9c1a1111",
          "name": "AC & Appliance Repair",
          "slug": "ac-appliance-repair",
          "description": "Repair and maintenance for home appliances",
          "image": { "key": "service-catalog/categories/uuid.jpg", "url": "https://cdn.example.com/service-catalog/categories/uuid.jpg" },
          "sortOrder": 0,
          "isActive": true,
          "createdBy": "665f1c2e8b1e4a2a9c1a0001",
          "updatedBy": null,
          "createdAt": "2026-01-01T00:00:00.000Z",
          "updatedAt": "2026-01-01T00:00:00.000Z"
        }
      ],
      "total": 1,
      "page": 1,
      "limit": 20
    },
    "message": "Categories retrieved",
    "success": true
  }
  ```
- **Errors:** none beyond generic validation.

#### `GET /api/v1/service-catalog/categories/:categoryId`
- **Access:** public.
- **Params:** `categoryId` — 24-hex ObjectId string (`objectIdSchema`).
- **Success 200:** same category shape as above, `data` is a single object, `message: 'Category retrieved'`.
- **Errors:** `404 Category not found` (`CategoryService.getById`).

#### `POST /api/v1/service-catalog/categories`
- **Access:** `authenticate` + `requireIdentity(admin)`.
- **Body (`createCategorySchema`):**
  | Field | Type | Required | Constraints |
  |---|---|---|---|
  | `name` | string | yes | trim, 2–100 chars |
  | `description` | string | no | trim, max 500 |
  | `image` | `{ key: string, url: string(url) }` | no | both subfields required if present |
  | `sortOrder` | number (coerced) | no | int |
  | `isActive` | boolean | no | |
- **Success 201:** created category object, `message: 'Category created'`.
- **Errors:** `400` Zod validation failure; `400` duplicate slug (11000, if `name` slugifies to one already in use).

#### `PATCH /api/v1/service-catalog/categories/:categoryId`
- **Access:** admin.
- **Params:** `categoryId`.
- **Body (`updateCategorySchema`):** all fields from create, all optional; refined to require **at least one** field present (`400 'At least one field must be provided'` otherwise).
- **Success 200:** updated category, `message: 'Category updated'`.
- **Errors:** `404 Category not found`; `400` validation; `400` duplicate slug.

#### `DELETE /api/v1/service-catalog/categories/:categoryId`
- **Access:** admin.
- **Success 200:** `data: null`, `message: 'Category deleted'`.
- **Errors:** `404 Category not found`; **`409 Cannot delete a category that still has subcategories`** (cascade guard — checked in `CategoryService.delete` via `Subcategory.exists({ category })`).

#### `DELETE /api/v1/service-catalog/subcategories/:subcategoryId`
- **Access:** admin.
- **Errors:** `404 Subcategory not found`; **`409 Cannot delete a subcategory that still has service groups`**.

### 3.5 Add-ons — `/api/v1/service-catalog/add-ons`

#### `GET /api/v1/service-catalog/add-ons`
- **Access:** public.
- **Query (`listAddOnsSchema`):** `page`, `limit`, `service` (objectId, optional), `serviceGroup` (objectId, optional), `isActive` (optional).
- **Success 200:** `{ items: AddOn[], total, page, limit }`, sorted by `name` asc, `message: 'Add-ons retrieved'`.

#### `GET /api/v1/service-catalog/add-ons/:addOnId`
- **Access:** public. **Errors:** `404 Add-on not found`.

#### `POST /api/v1/service-catalog/add-ons`
- **Access:** admin.
- **Body (`createAddOnSchema`):** `name` (2–100, required), `description` (optional, max 500), `price` (number, min 0, required), `image` (optional), `service` (objectId, optional), `serviceGroup` (objectId, optional), `isActive` (optional). Zod `.refine()`: **exactly one** of `service`/`serviceGroup` must be provided — `400 'Provide exactly one of service or serviceGroup'` otherwise.
- **Service behavior:** whichever of `service`/`serviceGroup` is given is checked to exist.
- **Success 201:** created add-on, `message: 'Add-on created'`.
- **Errors:** `404 Service not found` / `404 Service group not found`; `400` validation.

#### `PATCH /api/v1/service-catalog/add-ons/:addOnId`
- **Access:** admin.
- **Body (`updateAddOnSchema`):** all create fields optional; refined to require **at least one** field, and to disallow **both** `service` and `serviceGroup` being set together in the same request (`400 'Provide exactly one of service or serviceGroup'`) — but unlike create, it does **not** require one of them be present (you can update e.g. just `price` without touching the link).
- **Service behavior:** if you send `service`, the existing `serviceGroup` is cleared (set to `undefined`) before saving, and vice versa — this is required because the model's `pre('validate')` XOR check would otherwise reject a save that (temporarily) has both/neither set.
- **Errors:** `404 Add-on not found`; `404 Service not found` / `404 Service group not found` (if the provided link target doesn't exist); `400` validation.

#### `DELETE /api/v1/service-catalog/add-ons/:addOnId`
- **Access:** admin. **Errors:** `404 Add-on not found`.

### 3.6 Vendor Services — `/api/v1/service-catalog/vendor-services`

All routes require `authenticate` (applied once via `router.use(authenticate)` for the whole
sub-router); each route additionally requires a specific identity.

#### `POST /api/v1/service-catalog/vendor-services`
- **Access:** `authenticate` + `requireIdentity(vendor)`.
- **Body (`requestServiceSchema`):** `service` (objectId, required).
- **Behavior (`VendorServiceService.requestService`):**
  - The target `Service` must exist AND be `isActive: true`, else `404 'Service not found or inactive'`.
  - If a `VendorService` doc already exists for `{ vendor: req.user._id, service }`:
    - If its `status` is NOT `rejected` (i.e. `pending` or `approved`) → `409 'You already have a <status> request for this service'`.
    - If it IS `rejected` → the **same document is reset**: `status → pending`, `requestedAt → now`, `reviewedBy/reviewedAt/rejectionReason → null`. No duplicate document is created (enforced also by the unique `{ vendor, service }` index).
  - Otherwise a new `VendorService` doc is created with `status: pending`.
- **Success 201:** the `VendorService` document (new or reset), `message: 'Service requested'`.

#### `GET /api/v1/service-catalog/vendor-services/me`
- **Access:** `authenticate` + `requireIdentity(vendor)`.
- **Query (`listMyVendorServicesSchema`):** `page`, `limit`, `status` (optional, enum `pending|approved|rejected`).
- **Behavior:** filtered to `vendor: req.user._id`, populates `service` with only `name price duration isActive`, sorted `createdAt` desc.
- **Success 200:**
  ```json
  {
    "statusCode": 200,
    "data": {
      "items": [
        {
  ```

#### `GET /api/v1/service-catalog/vendor-services`
- **Access:** `authenticate` + `requireIdentity(admin)`.
- **Query (`listVendorServicesSchema`):** `page`, `limit`, `status` (optional). E.g. `?status=pending`.
- **Behavior:** no vendor filter (all vendors), populates `vendor` with `firstName lastName phoneNumber email` and `service` with `name price duration`, sorted `createdAt` desc.
- **Success 200:** same envelope shape as above but `vendor` is a populated object (not just an id) with those 4 fields, `message: 'Vendor service requests retrieved'`.

#### `PATCH /api/v1/service-catalog/vendor-services/:vendorServiceId/approve`
- **Access:** `authenticate` + `requireIdentity(admin)`.
- **Params:** `vendorServiceId` (objectId). No body.
- **Behavior:** requires current `status === 'pending'`, else `409 'Request is already <status>'`. Sets `status: approved`, `reviewedBy: req.user._id`, `reviewedAt: now`, `rejectionReason: null`.
- **Success 200:** updated `VendorService`, `message: 'Request approved'`.
- **Errors:** `404 Vendor service request not found`; `409` if not pending.

#### `PATCH /api/v1/service-catalog/vendor-services/:vendorServiceId/reject`
- **Access:** `authenticate` + `requireIdentity(admin)`.
- **Body (`rejectVendorServiceSchema`):** `rejectionReason` (string, required, trim, 3–500 chars).
- **Behavior:** requires current `status === 'pending'`, else `409 'Request is already <status>'`. Sets `status: rejected`, `reviewedBy`, `reviewedAt`, `rejectionReason` from body.
- **Success 200:** updated `VendorService`, `message: 'Request rejected'`.
- **Errors:** `404 Vendor service request not found`; `409` if not pending; `400` validation (missing/short `rejectionReason`).

### 3.7 Media — `/api/v1/service-catalog/media`

Entire sub-router is gated: `authenticate` + `requireIdentity(admin)` (applied via
`router.use(...)` before the one route).

#### `POST /api/v1/service-catalog/media/presigned-url`
- **Access:** admin.
- **Body (`presignedUploadUrlSchema`):**
  | Field | Type | Required | Constraints |
  |---|---|---|---|
  | `entity` | string | yes | enum of the **keys** of `CATALOG_MEDIA_FOLDERS`: `category`, `subcategory`, `serviceGroup`, `service`, `addOn` (camelCase — NOT the hyphenated route names) |
  | `fileType` | string | yes | enum: `image/jpeg`, `image/png`, `image/webp` |
  | `fileSize` | number | yes | positive, max `5 * 1024 * 1024` bytes (5MB) |
- **Behavior (`MediaService.generatePresignedUploadUrl`):** maps `entity` to an R2 folder
  (`category→categories`, `subcategory→subcategories`, `serviceGroup→service-groups`,
  `service→services`, `addOn→add-ons`), builds an object key
  `service-catalog/<folder>/<uuid>.<ext>`, and returns a presigned S3-compatible `PutObjectCommand`
  URL (Cloudflare R2 via `@aws-sdk/client-s3`) valid for **60 seconds**. The file itself never
  passes through this backend.
- **Success 200:**
  ```json
  {
    "statusCode": 200,
    "data": {
      "uploadUrl": "https://<r2-endpoint>/<bucket>/service-catalog/categories/1b2c...-uuid.jpg?X-Amz-Algorithm=...",
      "key": "service-catalog/categories/1b2c...-uuid.jpg",
      "url": "https://<R2_PUBLIC_URL>/service-catalog/categories/1b2c...-uuid.jpg",
      "expiresIn": 60
    },
    "message": "Presigned upload URL generated",
    "success": true
  }
  ```
- **Errors:** the service also re-checks `entity`/`fileType`/`fileSize` internally and can throw
  `400 Invalid entity type: <entity>`, `400 Invalid file type. Allowed: ...`,
  `400 File exceeds max size of 5MB` — but since the Zod schema already restricts all three inputs
  to valid values before the controller runs, these are effectively unreachable defensive
  backstops under normal use, not distinct behaviors a well-formed client would ever see.

## 4. Business rules / state machines

- **Catalog hierarchy integrity is enforced top-down at write time, not just by schema `ref`s:**
  creating/updating a `Subcategory` checks its `category` exists; creating/updating a
  `ServiceGroup`/`Service` derives (and validates) its parent chain via a Mongoose `pre('save')`
  hook that does a real `findById` lookup and throws `404` if the parent is missing.
- **Cascading delete guards (no cascading deletes — deletes are blocked instead):**
  - Category can't be deleted while it has any `Subcategory` (`409`).
  - Subcategory can't be deleted while it has any `ServiceGroup` (`409`).
  - ServiceGroup can't be deleted while it has any `Service` (`409`).
  - Service can't be deleted while it has any `VendorService` OR `AddOn` referencing it (`409`).
  - There is no soft-delete anywhere in this module — `delete` always calls `.deleteOne()` (hard
    delete) after the guard checks pass. `isActive: false` is the only "soft disable" mechanism,
    and it is a plain boolean flag with no automatic cascade (deactivating a `Category` does NOT
    automatically deactivate its subcategories/service groups/services — this is not implemented
    anywhere in the read files).
- **Slugs are always server-generated** (`slugify(name, { lower: true, strict: true })`) on
  create and whenever `name` changes; clients cannot set `slug` directly (it's not in any Zod
  schema). Uniqueness scope varies by level: `Category.slug` is globally unique; `Subcategory.slug`
  is unique per `category`; `ServiceGroup.slug` is unique per `subcategory`; `Service.slug` is
  unique per `serviceGroup`.
- **AddOn target XOR:** an add-on must link to exactly one of `service` / `serviceGroup`. Enforced
  twice: at the Zod layer (`create` requires exactly one; `update` forbids both together) and again
  at the Mongoose layer (`pre('validate')`, XOR check) as a backstop. When `update` switches the
  link from one type to the other, the service layer explicitly clears the other field before
  saving.
- **VendorService state machine:** `pending → approved` or `pending → rejected`, both admin-only
  and both **only valid from `pending`** — attempting to approve/reject an already
  approved/rejected request returns `409 'Request is already <status>'`. A vendor may re-request a
  previously **rejected** service, which resets the same document back to `pending` (not a new
  document — `{vendor, service}` has a unique index, so duplicates are impossible at the DB level
  too). Re-requesting a `pending` or `approved` existing request is blocked with `409`.
- **Duplicate-key errors surface as `400`, not `409`:** business-rule conflicts detected in the
  service layer (e.g. delete guards, re-request conflicts) throw `ApiError` with `409`; raw
  MongoDB duplicate-key errors (`code 11000`, e.g. a slug collision) are instead caught by
  `globalErrorHandler` and converted to `400` "Duplicate value for field '<field>'..." — a
  frontend should not assume all uniqueness violations are `409`.
- **`Service.rating` is populated/updated by something outside this module** — no
  service-catalog endpoint writes `rating.average`/`rating.count`; treat both as read-only in any
  UI built against this API.
- **Denormalized `category`/`subcategory` fields on `ServiceGroup`/`Service` are always kept in
  sync server-side** whenever the immediate parent reference changes (not just on create) — a
  client should never send `category` on a `ServiceGroup` create/update or `category`/`subcategory`
  on a `Service` create/update; they are silently ignored since they aren't in the Zod schemas at
  all (any such properties in the request body are stripped by `validate()`'s `safeParse`, which
  replaces `req.body` with only the schema-defined keys).

## 5. Frontend integration notes

- **Pagination is consistent across every list endpoint** in this module: query params `page`
  (1-based, default `1`) and `limit` (default `20`, max `100`), both coerced from strings. Every
  list response shape is `{ items: [...], total, page, limit }` (no `hasMore`/`totalPages` — compute
  `Math.ceil(total / limit)` client-side if needed).
- **`isActive` filters are string-typed** (`'true' | 'false'`, not booleans) across all list
  endpoints that expose it (categories, subcategories, service groups, services, add-ons). Passing
  anything other than the literal string `'true'` (including omission being different from passing
  `'false'`) — the service layer does `isActive === 'true'`, so `?isActive=false` and
  `?isActive=anything-else` both resolve to filtering on `isActive: false`. Omit the param entirely
  to get both active and inactive.
- **List sort order is NOT uniform** — it varies per entity and is not client-controllable (no
  `sort`/`order` query param exists anywhere in this module):
  | Endpoint | Sort |
  |---|---|
  | Categories | `sortOrder` asc, then `name` asc |
  | Subcategories | `sortOrder` asc, then `name` asc |
  | Service Groups | `sortOrder` asc, then `name` asc |
  | Services | `name` asc only (no `sortOrder` field exists on `Service`) |
  | Add-ons | `name` asc only |
  | Vendor Service requests (both `/me` and admin list) | `createdAt` desc (newest first) |
- **Filter param names differ slightly per level** by design (each only exposes filters relevant
  to its own ancestry): Subcategories filter by `category`; ServiceGroups filter by `category`
  and/or `subcategory`; Services filter by `category`, `subcategory`, and/or `serviceGroup`, plus a
  full-text `search` param (backed by a Mongo text index on `name`+`description` — no fuzzy/partial
  matching guarantees beyond MongoDB's own text search semantics); Add-ons filter by `service`
  and/or `serviceGroup`.
- **Writable vs. server-derived fields:** never send `slug`, `createdBy`, `updatedBy`,
  `createdAt`/`updatedAt` on any write. Never send `category` when creating/updating a
  `ServiceGroup`, or `category`/`subcategory` when creating/updating a `Service` — both are
  derived server-side from the immediate parent and will be silently dropped if sent (the Zod
  schemas don't declare them, so `validate()` strips them from `req.body`). `Service.rating` is
  fully read-only.
- **Image/media upload is a two-step, direct-to-storage flow (Cloudflare R2), not multipart or
  base64 to this backend:**
  1. Admin client calls `POST /api/v1/service-catalog/media/presigned-url` with
     `{ entity, fileType, fileSize }` (`entity` is one of the camelCase keys `category`,
     `subcategory`, `serviceGroup`, `service`, `addOn` — note `serviceGroup`/`addOn` are
     camelCase here even though their catalog routes are hyphenated `/service-groups`, `/add-ons`).
  2. Client `PUT`s the raw file bytes directly to the returned `uploadUrl` (valid 60 seconds) with
     header `Content-Type` matching `fileType`.
  3. Client then includes `{ key, url }` (exactly the `key`/`url` returned by step 1, NOT the
     `uploadUrl`) as the `image` field (or as one element of the `images` array, for `Service`) in
     the subsequent `POST`/`PATCH` to the catalog entity endpoint. The `imageInputSchema` Zod shape
     requires both `key` (non-empty string) and `url` (must parse as a URL).
  - Allowed MIME types for upload: `image/jpeg`, `image/png`, `image/webp`. Max size: 5MB
    (`5 * 1024 * 1024` bytes) — enforced both when requesting the presigned URL and (redundantly)
    inside `MediaService`.
- **Vendor-service workflow for a vendor-facing UI:** a vendor lists browsable, active `Service`
  records via the public `GET /services` endpoints, then `POST`s `{ service: <id> }` to
  `/vendor-services` to request to offer it. Poll/refresh `GET /vendor-services/me` (optionally
  `?status=pending`) to show request status. There is no vendor-facing cancel/withdraw endpoint in
  this module — only admin `approve`/`reject`. A vendor whose request was rejected can re-request
  the same service (same endpoint, same body) to flip it back to `pending`.
- **Admin permission model is coarse:** since this module never calls `checkPermission`, any
  authenticated `admin` identity can perform every write in this module — there is no
  finer-grained "catalog editor" vs. "vendor approver" split enforced here (see Overview section
  ambiguity note). If the product needs that split, it isn't implemented in this module as read.
- **Error shape differs from success shape** — do not assume `success`/`data` symmetry. Success
  responses are `{ statusCode, data, message, success: true }`; error responses are
  `{ success: false, status, message, errors? }` (key is `status`, no `data` key, `errors` only
  present when non-empty, e.g. Zod validation failures list `{ field: 'body.name', message }`
  entries).
